9. Do not fabricate external-provider responses, runtime results, test passes, database connections, or production readiness.
10. Do not automatically merge the backend branch into `dev`. Create a Draft PR and report the implementation and test results for review.

12. Favor farmer-friendly simplicity over technical complexity.

# B1 — Philippine Time, Backend Localization, Pagination, and Filtering

## A. Time Zone Standardization

The user wants all farmer-facing dates and times to use Philippine Standard Time, with sensible configurability.

Requirements:

1. Default farm time zone: `Asia/Manila`.
2. Retain UTC storage for timestamps that represent actual instants.
3. Use the farm's configured time zone for scheduling and date calculations.
4. Return unambiguous API timestamps with UTC or explicit offset information.
5. Ensure backend contracts provide sufficient information for localized display of:
   - Weather updates.
   - Notifications.
   - Tasks.
   - Farm activities.
   - Monitoring records.
   - Harvest history.
   - Inventory history.
   - Scheduled reminders.
   - Email timestamps.
6. Review `DateTime`, `DateTimeOffset`, `DateOnly`, and time-zone handling for correctness.
7. Preserve valid historical data and scheduled-job behavior.
8. Do not blindly replace all `DateTime.UtcNow` usages with Philippine local time.

Use one consistent, well-tested time conversion strategy.

## B. Localization Foundation

Prepare backend support for complete English and Filipino localization.

Requirements:

1. Use stable error/status codes rather than relying on English message text.
2. Support localizable validation errors, notification templates, email content, and weather guidance.
3. Provide a suitable mechanism for persisting a user's preferred language if the current architecture requires it.
4. Default to English for backward compatibility where no preference exists.
5. Support Filipino without changing machine-readable enum values or API contracts.
6. Separate stored business facts from their translated presentation.
7. Avoid hard-coded English-only generated notification text where translation is required.
8. Provide shared terminology and message identifiers for the frontend engineer.

The frontend engineer will translate and render the actual web and Android interfaces.

## C. Pagination and Filtering

Audit existing paging before adding new functionality.

Implement appropriate server-side pagination, search, filtering, and ordering for potentially large datasets, including:

- Farm tasks and task history.
- Monitoring observations and activities.
- Harvest records.
- Inventory and inventory movement history.
- Notifications.
- Farm membership/enrollment history where appropriate.
- Other large record lists identified by the audit.

Existing Admin pagination should be retained and improved only where necessary.

Requirements:

- Stable sorting.
- Defined page size and maximum limits.
- Correct total counts or continuation metadata.
- Consistent filter and sort parameters.
- Farm authorization enforced before querying records.
- Proper behavior when records change between requests.
- No destructive changes to existing client contracts.
- Existing web/Android clients must continue working.
- Android offline synchronization must remain complete, independent of ordinary list pagination.

Prefer additive version-compatible endpoints or optional parameters where appropriate.

### Deliverables

- Stable local-time contracts.
- Backend localization foundation.
- Pagination/filtering services and APIs.
- Documented contracts and comprehensive tests.

## Existing Foundation

The system already uses Open-Meteo, saved weather forecasts, weather rules, Hangfire checks, advisories, and in-app notifications.

Inspect and reuse these components.

## A. Weather Improvements

Support intuitive weather categories such as:

- Recent updates.
- Active warnings.
- Upcoming forecast.
- Previous/resolved advisories.
- Weather history, if retained and useful.

Requirements:

1. Provide normalized weather categories and filterable API data.
2. Preserve weather source, retrieval time, validity, and staleness metadata.
3. Distinguish forecast-based advisories from official emergency warnings.
4. Preserve the existing reliable rule-based detection logic.
5. Review rainfall, wind, and heat thresholds for correctness and clear classification.
6. Never treat a missing weather reading as proof that a warning has cleared.
7. Retain alert deduplication.

9. Preserve worker scheduling and provider-failure recovery.
10. Never describe an outdated forecast as current conditions.

- Acknowledgment/dismissal information where needed.

Recommendations:

# B3 — Email Integration and Secure Account Recovery

Implement production-appropriate email support using existing ASP.NET Core Identity infrastructure.

## A. Forgot Password

Support web and Android clients.

Required workflow:

1. User requests a password reset using their email.
2. API responds neutrally regardless of account existence.
3. Valid users receive a secure time-limited reset link/token.
4. Reset request and completion are rate-limited.
5. Token verification and password validation are performed securely.
6. A completed reset follows an appropriate existing-session/token revocation policy.
7. User receives a confirmation of the security-sensitive action where appropriate.
8. Invalid, expired, or reused tokens are handled safely.
9. Email-delivery failures are logged securely without leaking sensitive details.

Implement the required backend MVC actions and API contracts, but leave Razor/Compose presentation to the frontend engineer.

## B. Email Infrastructure

1. Provide a configurable email-sending abstraction.
2. Integrate with a suitable transactional email provider or SMTP implementation only when appropriately configured.
3. Keep provider credentials in secrets/environment configuration.
4. Do not hard-code secrets or expose them to Android.
5. Provide local/test email delivery with a safe fake sender.
6. Use English/Filipino-ready templates.
7. Include appropriate Philippine-local formatted timestamps where applicable.
8. Ensure email links use a validated, configured application origin to prevent hostile reset URLs.

## C. Additional Useful Emails

Prioritize:

- Password reset.
- Password/security change alerts.
- Important account-security notifications.
- Farm enrollment approval/rejection notifications, if useful and permitted.

Routine task reminders and weather digests should be optional, preference-controlled, and not implemented as an uncontrolled email-spam feature.

### Deliverables

- Email delivery abstraction.
- Password recovery API/MVC backend.
- Security safeguards.
- Automated tests.
- Documented provider configuration and frontend contracts.

# B4 — Gemini Integration: Phases A–C

Implement the agreed three-stage weather intelligence system.

## Phase A — Reliable Rule-Based Weather Foundation

The system already has weather rules and saved advisories.

Verify and improve:

- Forecast ingestion and validity.
- Weather threshold evaluation.
- Existing advisory generation.
- Severity logic.
- Duplicate prevention.
- Notifications.
- Freshness and stale-data detection.
- Background job reliability.

Do not rebuild this foundation unnecessarily.

## Phase B — Gemini Explanations

Implement Gemini as a server-side explanation service for weather advisories.

Requirements:

1. Keep API credentials exclusively on the backend.
2. Send only the minimum necessary weather and farm context.
3. Generate simple, understandable, farmer-friendly explanations.
4. Support English and Filipino.
5. Use validated, structured responses.
6. Establish request timeouts, retry limits, quotas and cost controls.
7. Cache suitable repeated explanations.
8. Log failures without leaking personal information or credentials.
9. Fall back to original deterministic weather guidance when Gemini is unavailable.
10. Keep warnings traceable to the actual weather data and source.

Gemini must not change the original forecast or determine emergency severity independently.

## Phase C — Crop-Aware Recommendations

Extend Phase B with permitted farm context:

- Crop type.
- Crop growth/lifecycle stage.
- Relevant plot information.
- Selected recorded conditions.
- Forecast/advisory context.

Produce practical recommendations such as checking drainage, postponing weather-sensitive work, or inspecting crops for stress.

Requirements:

1. Suggestions must remain advisory.
2. Never automatically modify crop records, irrigation, inventory, task assignments, or harvest plans.
3. Do not fabricate farm readings or imply unverified conditions.
4. Do not provide unsupported precise chemical/application recommendations.
5. Indicate limitations when sufficient data is unavailable.
6. Keep outputs structured and validated.
7. Respect farm authorization and data minimization.
8. Provide usable non-AI fallback recommendations.
9. Support localization.
10. Add comprehensive tests using mocked Gemini responses, including malformed output, quota errors, timeouts, and prompt-injection attempts from user-entered farm text.

If Gemini provider configuration is unavailable, implement a clean, testable adapter and integration contracts without claiming successful live-provider execution.

### Deliverables

- Verified Phase A.
- Gemini Phase B explanation service.
- Phase C crop-aware recommendation service.
- Secure API integration and frontend DTOs.
- Tests and configuration documentation.
