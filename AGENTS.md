# SmartFarm development conventions

- **Project brief:** Build the Smart Farm and Crop Monitoring Management System with MVC farms/plots, crop calendars, inventory and harvest reports; an API for farm activities, observations, supply and harvest records; Hangfire weather checks and reminders; Kotlin field inspections/photos and Room-based offline activities; and a suitable external weather API.
- **ASP.NET references:** Follow `Stephware/CampusEquipment` for distinct Core/Infrastructure/API/Web projects, explicit `IThingRepository` + `ThingRepository` interfaces and implementation pairs, `IThingService` + `ThingService`, EF Core queries in repositories, and model-bound Razor forms with Tag Helpers and validation messages. Follow `KurtSarmiento/AspNetCoreMultiApp` for separate MVC, API, Worker hosts and typed `HttpClient` calls; also consult `Stephware/VeterinaryClinicSystem` and `Stephware/MyWebApi`.
- **Android references:** Follow `Stephware/RoomDatabaseDiscussion` for Kotlin Room Entity/DAO/Database/Repository/ViewModel/StateFlow/Compose patterns; `Stephware/ComposeUIEssentials` for `NavHost` / navigation; `Stephware/MobdevMidtermExam` for Compose Material 3 screen/forms and conventional Kotlin syntax. For saved Compose UI state import `androidx.compose.runtime.saveable.rememberSaveable`. Preserve separate Retrofit API repositories for online operations.
- **Scope and compatibility:** Keep .NET 10, Android Kotlin/Compose, existing SQL-first `SmartFarmDB` schema and mapped tables. No automatic migrations, database recreation, CI/CD, or unrelated refactoring. Complete the phases one at a time **only when the user explicitly requests the next phase**. Worker/automation/offline sync are planned later.
- **Code quality:** Prefer concise, readable class/function names and familiar activity syntax; do not blindly copy activity code when production authentication, farm permissions, transactions, or synchronization require additional safeguards. Test before claiming a build passes and distinguish source inspection from runtime checks.
- **Documentation:** Keep docs minimal: README, essential setup/verification notes and genuine architecture decisions; avoid routine extra per-feature documents.
- **Git:** Feature branches and PRs to `dev`, regular merge commits (no squash/rebase). **Every commit description and PR summary must be only 1–3 sentences.** Keep user-facing progress and explanations short, accurate and easy to follow.
